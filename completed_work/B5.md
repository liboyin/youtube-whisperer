# B5 — Title-only filenames silently alias different videos

## Origin

A 2026-09 assessment ([historical assessments](history.md#evidence-provenance)) classified B5 as Blocking with High severity, validated by source inspection and an isolated equal-title reproduction. Video and caption default names came from the sanitized, truncated title alone, so different videos could share MP4/SRT paths. Under the worker's `NEVER` policy, the second video then reused the first video's media and possibly its captions.

The fix waited on a user decision about naming and migration. The 2026-09-14 simplification review also asked for one naming rule for standalone and combined downloads.

## Decisions

[D47](../DESIGN.md#d47) records three user decisions, all from 2026-10-14:

- **Naming:** default names are `Title [videoID].ext`, which keeps the library browsable by title. ID-only names and adding the ID only on collision were rejected.
- **Migration:** files are not renamed. A title-only file is reused when the ID-tagged name does not exist, and the user accepted that this keeps title-only aliasing for existing files.
- **Fallback exception:** after the review below, a title-only name ending in an 11-character ID-shaped tag other than the video's own ID is never reused.

Following [D46](../DESIGN.md#d46) step 3, pathlib-extensions `build_filename` (commit `09cab14`) builds the name.

## Boundary

- **Intent:** different videos never share a default file, and repeat downloads of the same video map to the same file.
- **Direction:** everything lives in [downloaders/utils.py](../youtube_whisperer/downloaders/utils.py):
  - `_extract_video_info` is shared by the unchanged `get_video_title` and the new `get_video_title_and_id`. One yt-dlp metadata request supplies the title and `info['id']`, so non-YouTube URLs keep working.
  - `default_media_filename` builds the ID-tagged name.
  - `legacy_media_filename` reproduces the pre-B5 name, returning None when that rule could not have produced a file.
  - `resolve_default_media_path` picks between them. Both default-title download functions use it, and the combined download still derives its SRT path from the video path.
- **Compatibility ([D18](../DESIGN.md#d18)):**
  - Signatures and return types are unchanged; default names change as D47 records.
  - `get_video_title` still returns the title.
  - An empty title now raises `ValueError` instead of producing a hidden `.mp4` or `.srt`.
- **Non-goals:**
  - renaming files;
  - ownership metadata;
  - recovering collisions that already happened.

## Change

- **Naming:** `default_media_filename(title, video_id, suffix)` is `build_filename(title, suffix, tag=' [sanitized id]', max_length=220)`. Only the title is truncated, so the ID tag and suffix always survive.
- **Path choice:** `resolve_default_media_path` returns, in order of preference:
  - the ID-tagged path, if it exists;
  - a legacy title-only *regular file*, unless its stem ends in another video's ID-shaped tag (`TRAILING_VIDEO_ID_TAG`, anchored with `\Z`);
  - otherwise the ID-tagged path.
- **Pin:** [requirements.txt](../requirements.txt) moves to pathlib-extensions `09cab14484733c63e3062c071202444be9daa5668`.
- **Tests:**
  - the naming rule;
  - the legacy cases (reuse, prefer tagged, ignore directories, absent legacy name, own-ID tag, ordinary brackets, trailing newline);
  - the foreign-tag overlap through the standalone video, standalone caption and combined paths;
  - the updated caller tests.
- **Documentation:**
  - DESIGN's "Filenames carry the title and video ID" section replaces "Filenames are truncated".
  - The SRT paragraph that called naming unresolved is updated.
  - DESIGN's project tree describes `downloaders/utils.py` as holding the default filenames.
  - README's usage section explains the `Title [videoID].ext` names and title-only reuse.
  - Links from NB8, NB34 and NB37 now point here.

## Review

- **Reviewer:** Codex thread `01a137c9-3d3c-7b33-a1be-cfc76572c554`. Its model, `gpt-6.1-sol`, and effort, `high`, come from the dispatch command.
- **Round 1, Blocking:** the legacy fallback accepted another video's new ID-tagged file. Video B titled `Title [aaaaaaaaaaa]` resolved to video A's `Title [aaaaaaaaaaa].mp4`, and the combined path reused A's media and captions.
  - **Validated:** any match between a legacy name and a generated name means the legacy stem ends in that ID tag.
  - **Fixed** under the user's decision (the third bullet in D47 above), with standalone and combined overlap tests.
- **Round 2, Non-blocking:** `$` also matched before a trailing newline. **Validated and fixed** with `\Z` and a test.
- **Round 3:** no unresolved findings. The reviewer's 14 probes passed, including real publication through the combined path.

## Limitations and cleanup

- **Accepted aliasing:** title-only files that existed before this change can still be reused for a different video with the same title (accepted in D47).
- **Rare re-downloads:** an old file whose real title ends in an ID-shaped tag is downloaded again, as are non-YouTube IDs that happen to have that shape.
- **Remote install not exercised:** the library commits needed a user push first, and pip installation from the remote was not exercised.
- **Reinstall required:** existing environments need dependencies reinstalled.
- **Cleanup:** working evidence lived in temporary session storage; its essentials are preserved here.
