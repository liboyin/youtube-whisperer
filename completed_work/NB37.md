# NB37 — Publication and overwrite preflight belong in pathlib-extensions

## Origin

After [NB34](NB34.md) the user asked whether `youtube_whisperer/publication.py` belonged in [pathlib-extensions](https://github.com/liboyin/pathlib-extensions). The main agent proposed moving it, together with the overwrite preflight that seven callers repeated (`if path.is_file() and not overwrite_existing_path(path, mode)`). The survey also found the `truncate_filename` defect recorded as [NB36](NB36.md).

The user then decided [D46](../DESIGN.md#d46) on 2026-10-13:

- fix `truncate_filename` first;
- move only the low-level publication functions and one preflight helper;
- keep library `print()` messages;
- the user pushes library commits before this project updates its pin.

NB36 and NB37 share one commit because both need the same pin update. This file holds the shared evidence.

## Boundary

- **Intent:** the library owns the publication steps (target resolution, mode retention, create-if-absent and replacement) and the existing-output preflight. This project imports them, keeps `youtube_whisperer.publication` as a forwarder under [D18](../DESIGN.md#d18), and removes the seven preflight copies.
- **Behavior preserved:**
  - Only an existing file (`is_file()`) is checked, so a directory still fails later in `prepare_output_file`.
  - A declined overwrite returns what it did before: None for video and WAV, the output path for the SRT functions and transcribers, True for caption download.
  - PROMPT is asked once.
  - An approved PROMPT now becomes ALWAYS for every caller. Whisper and Azure already did this, and publication treats PROMPT and ALWAYS identically.
- **Compatibility surface:** public signatures and return values of the video, caption, SRT, WAV, Whisper and Azure functions are unchanged. `youtube_whisperer.publication` still exports `publish_staged_file` and `resolve_publication_target`. Only the incidental `overwrite_existing_path` attribute of the seven caller modules was removed.
- **Non-goals:**
  - [B5](B5.md) naming and moving title-to-filename construction (D46 step 3);
  - a create-publish-clean-up context manager;
  - stage handling;
  - logging.

## Library changes

The user pushes these commits. The changes were checked on Python 3.12.3 only; 3.10 and 3.11, which the library's CI also runs, were not available locally.

### `c70c0c5` — truncate_filename

This is the [NB36](NB36.md) fix:

- It keeps the trailing run of extension-like suffixes (a dot followed by ASCII letters or digits).
- It cuts the stem at a UTF-8 character boundary.
- It raises `ValueError` when no whole stem character fits, or when the result would be `.` or `..`.

Validation and mutation evidence:

- Library pytest gave 56 passed and mypy was clean.
- Mutants T1–T12 ran in a scratch copy with import provenance checked on every run, seed 20261013. All non-equivalent mutants were killed:
  - the old any-suffix rule;
  - keeping only the last suffix;
  - allowing hyphens, underscores or Unicode word characters;
  - lowercase-only extensions;
  - no empty-stem check;
  - no clamp for an over-limit suffix;
  - strict decoding;
  - the old slicing;
  - no `.`/`..` guard.
- T5, which truncates at exactly the limit, survives as equivalent. It returns the same path and only adds a print.

Review: Codex thread `01a1356f-54b4-7fe1-a8f0-f52d29f4257d` (`gpt-6.1-sol`, high, per the dispatch command).

- **Round 1, Blocking:** nothing tested the suffix character boundary. Mutants allowing `-`, `_` or Unicode `\w`, or lowercase only, all survived. Fixed with parametrized hyphen/underscore/non-ASCII tests and an uppercase-extension test.
- **Round 1, Non-blocking:** limits of 1–3 bytes could truncate a leading-dot name to `.` or `..`. This was inherited from `3f39af6`. Fixed with a guard and tests.
- **Follow-up:** the reviewer replayed T1–T12; both findings were resolved and none remained.

### `88aba06` — publication and preflight

- `publication.resolve_publication_target` and `publish_staged_file` have the same executable behavior as this project's NB34 helper; the reviewer compared the AST. Their docstrings now state:
  - the same-filesystem hard-link requirement;
  - that there is no fallback when hard links are unsupported;
  - the D22 metadata and alias consequences;
  - that nothing is fsynced.
- `overwrite.resolve_overwrite_mode(path, mode) -> OverwriteMode | None` is the shared preflight.
- On Python 3.10, `Path.replace` binds `os.replace` when pathlib is imported, so the library's replacement-failure test patches `Path.replace`.

Validation and mutation evidence:

- Library pytest gave 100 passed, with `publication.py` and `overwrite.py` at 100%; mypy was clean.
- In a fresh scratch copy with provenance checked (baseline 56 passed), every mutant was killed:

| Mutant | Failed tests |
|---|---|
| M1 skip chmod | 11 |
| M2 swallow every `FileExistsError` | 4 |
| M3 re-raise every `FileExistsError` | 4 |
| M4 replace under NEVER/RENAME | 12 |
| M5 create-if-absent for every mode | 4 |
| M6 no `.resolve()` | 3 |
| M7 resolved target not prepared | 3 |
| M8 chmod after publication | 8 |
| P1 `exists()` instead of `is_file()` | 3 |
| P2 approved PROMPT not turned into ALWAYS | 1 |
| P3 decline returns the mode | 4 |

Review, same Codex thread:

- **Round 1, Blocking:** no test protected applying the mode before publication. M8 passed, yet with a failing chmod it would replace the old file before raising. The same gap existed in NB34's helper. Fixed with `test_publish_staged_file_mode_failure_publishes_nothing` (four modes, existing and absent targets).
- **Follow-up:** the reviewer replayed M1–M8 and P1–P3; the finding was resolved and none remained.
