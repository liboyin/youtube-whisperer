# NB35 — Consumer groups recreated at `$` strand entries appended while the group was absent

## Origin

A main-agent gap review of the API group (`e3ad2a6..b4a59da`, 2026-10-11) found this issue by source inspection. It did not use the adversarial-review skill. The user asked for all gaps to be fixed. NB35 was given an ID, fixed, and closed in the same commit.

`ensure_consumer_group` created a missing group with redis-py's default start ID `$`. Workers recover from `NOGROUP` through the same function. Suppose `DELETE /tasks` deleted a stream, and with it the group, after a submitter had created the group but before its `XADD`. The `XADD` then recreated the stream without a group, and the recovering worker created the group after that entry. The task was never delivered, while `GET /tasks` showed it as pending indefinitely. NB15 made this race reachable between two API requests. The YouTube worker's follow-up submissions could already race `DELETE /tasks` in the same way.

## Boundary

Create a missing group so that it delivers every entry already in its stream. Compatibility surface: the `ensure_consumer_group` signature, the worker loop and the HTTP contracts are unchanged. Only the wording of `DELETE /tasks` in DESIGN is clarified.

Non-goals:

- making `DELETE /tasks` atomic: under [D6](../DESIGN.md#d6), an entry appended to a stream that is then deleted can still be lost;
- exactly-once delivery.

The gap review offered two options: fix the start ID, or document the stranded outcome under D6. The user asked for the fix, which is recorded as [D43](../DESIGN.md#d43).

## Revalidation

At `b4a59da`, every processed entry is acknowledged and deleted. This happens after success and after a durable dead letter (`workers/common.py`, the `run` loop). Any entry left in a stream is therefore unprocessed, so creating the group from ID `0` delivers only work still owed. If a group already exists, Redis returns `BUSYGROUP` and the group is not changed. redis-py 8.1.0's `xgroup_create` takes `id` with a default of `$`, documented as the "ID of the last item in the stream to consider already delivered".

## Change

[queueing.py](../youtube_whisperer/queueing.py) now calls `xgroup_create(stream, group, id='0', mkstream=True)`. Its docstring explains the race and why creating from `0` is safe. The test, renamed `test_ensure_consumer_group_creates_missing_group_from_stream_start`, asserts the start ID; the `BUSYGROUP` and other-error tests are unchanged.

DESIGN changes:

- a "Group creation" bullet under Redis Streams;
- the `DELETE /tasks` contract row now states that a concurrent submission which recreates a deleted stream is still delivered;
- the D43 decision row.

## Limitations and cleanup

The test checks the command contract on a Redis double. Redis's own handling of `$` and `0` is not exercised, because automated tests must not use a real Redis server, and no live race was reproduced. A manually destroyed group whose stream still holds in-flight entries would redeliver them, which is consistent with the documented duplicate tolerance. The scratch copy was deleted, and unrelated untracked files were preserved.
