# NB19 — Caption HTTP requests are bounded by a timeout

**Origin:** TODO recorded that transcript listing and fetching used the default `youtube-transcript-api` client. Its ordinary `requests` session performs GET and POST requests without timeouts, so a stalled response could occupy the single YouTube worker indefinitely. NB19 was implemented together with [NB24](NB24.md) as one cohesive change; the shared decisions, validation, mutation evidence and review are recorded there.

**Revalidation (`f047cda`, 2026-10-10):** inspection of the installed `youtube-transcript-api==1.2.4` and `requests==2.34.2` showed three things:

- `YouTubeTranscriptApi(http_client=...)` accepts a `requests.Session`.
- Listing (watch-page GET and innertube POST) and fetching (caption GET) all use that one session: `TranscriptList.build` hands it to each `Transcript`.
- `requests` has no session-level default timeout.

The application created a session through `YouTubeTranscriptApi()` and never closed it.

**Decision (user, 2026-10-10):** a fixed timeout of 10 seconds to connect and 30 seconds to read, applied per request as a module constant and not configurable. The user preferred this to a configurable setting or a wall-clock watchdog, accepting that slow-drip responses remain unbounded. This is recorded as [D38](../DESIGN.md#d38).

**Boundary:** the shared group constraints are in [NB24](NB24.md#boundary).

- **NB19 direction:**
  - A session subclass defaults every request to the timeout without overriding a caller's explicit timeout.
  - The session is owned per caption download, stays open from listing through fetching, and is closed on the success, missing-caption and failure paths.
  - Timeouts propagate out of `TranscriptDownloader`, and NB24 handles them after the media download.
- **NB19 acceptance:**
  - A controlled HTTP double shows that all three request kinds carry `(10, 30)`.
  - A simulated stall fails within that bound and visibly.
  - The session is closed on every path.
  - Explicit timeouts are preserved.

**Change:**

- [transcript_downloader.py](../youtube_whisperer/downloaders/transcript_downloader.py) adds `CAPTION_HTTP_TIMEOUT = (10, 30)` and `CaptionSession(Session)`, whose `request` is `partialmethod(Session.request, timeout=CAPTION_HTTP_TIMEOUT)`. Call keyword arguments override the partial default, so an explicit `timeout`, even `None`, wins.
- `TranscriptDownloader.download` opens `with CaptionSession() as http_client` around both listing and fetching.
- The public `list_video_transcripts(url, http_client=None)` uses a supplied session without closing it. When the session is omitted, it creates a fresh `CaptionSession`, which stays with the returned `TranscriptList` for later fetches. This keeps the one-argument call working under [D18](../DESIGN.md#d18), with the same lifetime as the old default client, and adds the timeout. The first candidate made the parameter required; the review blocked that, as described in [NB24](NB24.md#review).

**Acceptance evidence** (`tests/downloaders/test_transcript_downloader.py`, using the owned `caption_http` fixture described in [NB24](NB24.md)):

| Acceptance criterion | Tests |
| --- | --- |
| Watch GET, innertube POST and caption GET each carry `(10, 30)` through the real library code | `test_download_applies_timeout_to_watch_innertube_and_caption_requests` |
| A stall in any phase, simulated by `ReadTimeout` when a timeout is finite, propagates the same exception and closes the session | `test_download_timeout_propagates_and_closes_owned_session` |
| Disabled captions or an unmatched language return `None` and close the session | `test_download_missing_captions_closes_owned_session` |
| Explicit `(2, 3)`, `4` and `None` timeouts are preserved | `test_caption_session_preserves_explicit_keyword_timeout` |
| The legacy one-argument (and explicit `None`) listing call works, every request carries `(10, 30)`, and the default session stays open through a later fetch | `test_list_video_transcripts_legacy_call_retains_timeout_session_for_later_fetch` |
| A timeout after a successful media download falls back under D16 | NB24's orchestration and worker tests (`ReadTimeout`/`ConnectionError` cases) |

**Validation, mutation evidence, review, limitations and cleanup:** shared with NB24; see [Validation](NB24.md#validation), [Mutation evidence](NB24.md#mutation-evidence), [Review](NB24.md#review) and [Limitations and cleanup](NB24.md#limitations-and-cleanup). The NB19 mutants were: timeout omitted, timeout during listing only, session not closed, explicit timeout overridden, parameter required again, and legacy default session without a timeout. All were killed.

**Limitation specific to NB19:** the read timeout bounds silence between bytes, not total transfer time. A real stalled socket was not exercised: the double raises `requests` timeout errors, and the claim that `requests` enforces them at the socket rests on its documented `HTTPAdapter.send` behaviour.
