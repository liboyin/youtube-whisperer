# NB47 — Install dev tools through the PyPI mirror

## Origin

After [NB46](NB46.md), the image installed every runtime package through `PYPI_PROXY`, but the devcontainer creation hook added the `dev` group with `uv sync --locked` directly from PyPI. That was the only way at the time, because a lock resolved against PyPI is reported stale behind the mirror. On 2026-11-06 the user asked for this to be mitigated, because their internet connection can be unstable. Of three options, they chose a separate `dev` Dockerfile target ([D52](../DESIGN.md#d52)). The rejected options were dev tools in every production image and a hook-time install through the mirror, which would have copied the shared helper's proxy logic into this repository.

## Boundary

- **Intent:** every PyPI package, dev tools included, comes through the `PYPI_PROXY` mirror when it is set, so creating the devcontainer needs no PyPI access.
- **Dependencies:** [D50](../DESIGN.md#d50) and NB46 (`5e03eb2`, with the update script in `c81f10a`); docker-build-common `v1.2.0` `uv_install.sh`, unchanged.
- **Direction:**
  - The Dockerfile's stage is named `runtime`, and a `dev` stage `FROM runtime` runs `uv_install.sh /opt/venv --group dev`. It redeclares `ARG PYPI_PROXY`, because a Dockerfile `ARG` only applies within its stage.
  - The shared Compose build anchor sets `target: runtime`.
  - The new `.devcontainer/docker-compose.devcontainer.yaml` sets `app.build.target: dev`, and `devcontainer.json` lists it after `../docker-compose.yaml`.
  - The creation hook installs nothing. It runs `uv lock --check --offline` and prints its own message when the lock is stale.
  - Documentation is updated, and standalone builds name `--target runtime`.
- **Compatibility surface:**
  - Production `docker compose up` (GPU and CPU) still builds every service from the lean image, now `runtime`.
  - The devcontainer's `app` image gains the dev tools, while the workers it starts keep `runtime`.
  - A standalone `docker buildx build` without `--target` now builds `dev`, the last stage, so README and the Dockerfile document `--target runtime`.
  - No Python API, HTTP or CLI behavior changes.
- **Non-goals:**
  - Mirroring non-PyPI downloads: GitHub (the build context and the `pathlib-extensions` git dependency), ghcr, deno.land, the NVIDIA base image, and the Claude/Codex installers.
  - Resolving `update-dependencies.sh` through the mirror, which would record mirror URLs in the lock.
  - Library changes.
- **Done:** both targets get every PyPI package from the mirror; the hook makes no network request for Python packages; production services build `runtime`; gates pass; the review is clean.

## Change

- **Dockerfile:**
  - The stages are now `runtime` and `dev`, and the header comment explains both.
  - The comments on `UV_PROJECT_ENVIRONMENT` and venv ownership now cite `update-dependencies.sh`, which is now the only thing that runs `uv sync`.
  - The standalone build example passes `--target runtime`.
- **Compose and devcontainer:**
  - `docker-compose.cpu.yaml` sets `target: runtime` in its build anchor, which the GPU file inherits through `extends`.
  - The new `.devcontainer/docker-compose.devcontainer.yaml` override sets `app` to `dev`, and `.devcontainer/devcontainer.json` layers it on.
- **Creation hook:** `postCreateCommand.sh` replaces `uv sync --locked` with `uv lock --check --offline`. On failure it says `uv.lock does not match pyproject.toml; run 'uv lock' and then 'uv sync --locked'` and exits 1 before the CLI installers run.
- **Docs:** README (Dev Container, standalone build, `PYPI_PROXY` row, Updating dependencies) and DESIGN (the uv section and D52, which supersedes D50's direct-PyPI dev install).

## Limitations and cleanup

- **Not performed (no Docker):**
  - A real BuildKit build of both targets.
  - A VS Code devcontainer rebuild, confirming the dev tools are present, the hook passes offline, and `git status` stays clean.
  - A Compose smoke run on GPU and CPU.
  - A production-image check that dev tools are absent.

  The user is to run these on the host.
- **Still online:** a user-configured uv index makes the offline check fail even for a current lock. Refreshing the lock (`update-dependencies.sh`) still needs PyPI, and the non-PyPI downloads listed under the non-goals still need their own networks.
- **Cleanup:** the scratch mirror process was stopped. Working evidence stayed in session scratch only, and this record keeps its essential content.
