# NB46 — Migrate dependency management to uv

## Origin

[NB5](NB5.md) recorded that `pip freeze` rewrote `requirements.txt` on every devcontainer create. The user refreshed dependencies by emptying that file and rebuilding without cache, which produced the periodic "Updated dependencies" commits. On 2026-11-06 the user asked to migrate to uv and settled the choices recorded as [D50](../DESIGN.md#d50): a full uv project, a venv instead of the system Python, apt Python 3.12, a `dev` dependency group, a new shared helper beside the pip one released under a new tag, and a first lock seeded with the snapshot's versions. They also decided to stay on Python 3.12 ([D51](../DESIGN.md#d51)). The plan and decisions were committed first, as `623543a`.

## Boundary

**Validated — revision aa840df on 2026-11-06; user-requested change under [D50](../DESIGN.md#d50).** Moved here unchanged from TODO at closure.

**Intent.** Replace the `pip freeze` snapshot with a uv lock: dependencies resolve from `pyproject.toml` into a committed `uv.lock`; the image installs that lock into `/opt/venv` through a shared `docker-build-common` helper; the devcontainer adds the locked `dev` group; and the lock changes only when someone runs `uv lock`. This resolves [NB5](NB5.md).

**Dependencies.** [D50](../DESIGN.md#d50) and its recorded proxy evidence; [D45](../DESIGN.md#d45) and [D51](../DESIGN.md#d51) (Python 3.12); the [build-helper design](../DESIGN.md#build-helpers-come-from-a-shared-repository); [D10](../DESIGN.md#d10) (the devcontainer starts the workers). The library helper must be pushed and tagged by the user before this repository's pin resolves without `BUILD_COMMON_CONTEXT`.

**Implementation direction — `docker-build-common` (local clone `/workspaces/docker-build-common`, branch `uv` from `main` at 1b8c221).** Add `uv_install.sh <venv-dir> [uv-export-option]...`, leaving `apt_install.sh` and `pip_install.sh` unchanged. Run from the project directory, the helper:

1. Fails with exit 2 when no venv directory is given or `uv` is not on `PATH`, and with exit 1 when `uv.lock` is missing.
2. Maps a non-empty `PYPI_PROXY` to `UV_DEFAULT_INDEX`, plus `UV_INSECURE_HOST` for the derived hostname, matching `pip_install.sh`'s `index-url`/`trusted-host` semantics. These are set for the helper's own processes only and never written to persistent uv configuration, because a persistent index would make later `uv lock` runs record the proxy URL in the lock.
3. Disables the uv cache, so no cache is left in the layer.
4. Creates the venv if absent (`uv venv --allow-existing`), honouring the consumer's `.python-version` and uv environment.
5. Exports the lock with `uv export --frozen --no-default-groups --format requirements.txt` plus forwarded options, to a temporary file it removes afterwards. `--frozen` is required because `--locked` fails behind a mirror (D50 evidence).
6. Installs the export with `uv pip sync`, which makes the venv exactly match the export and verifies every hash present. When the export contains no requirements it reports that and skips the install.

Without `--no-emit-project` the export includes the project itself, editable by default, so one helper serves both the dependency layer and the project install, and both go through the proxy. Bytecode is not precompiled, matching `pip_install.sh`. `tests/run.sh` gains cases that put a stub `uv` on `PATH` to record arguments and environment, without network access. README documents the helper. The intended release tag is `v1.2.0`: a minor version, because the change only adds a script (an assumption; the user owns tagging).

**Implementation direction — this repository.**

## Change

**This repository:**

- `pyproject.toml`: the `dev` optional extra became the `dev` dependency group.
- `.python-version` (`3.12`) and `uv.lock` were added, and `requirements.txt` was deleted.

  - copies uv 0.13.7 pinned by tag and digest (`sha256:96f40d39…b490`);
  - sets `VIRTUAL_ENV`, `UV_PROJECT_ENVIRONMENT=/opt/venv`, `UV_PYTHON_DOWNLOADS=never` and `PATH`;

It changes into the repository root, runs `uv lock --upgrade` (or one `--upgrade-package` per named package, rejecting option-like arguments with exit 2), then `uv sync --locked`, and stops at the first failure.

## Removed-layer ownership

- **The `pip freeze` step** had one unique behavior, regenerating the lock. That now belongs to explicit `uv lock` commands, as README describes; nothing regenerates the lock implicitly.
- **`pip_install.sh`** carried four behaviors, each with a new owner in `uv_install.sh`:
  - **Proxy index and trusted host:** `UV_DEFAULT_INDEX` and `UV_INSECURE_HOST`, kept process-local.
  - **No cache:** `UV_NO_CACHE`.
  - **No bytecode:** uv's default.
  - **Fail on a missing lock:** exit 1 without `uv.lock`.
- **`break-system-packages`** has no successor because nothing installs into the system Python any more.
- **The `python` symlink** existed only for the Compose entrypoints, and the venv's `python` now serves them.
- **`python3-pip`:** nothing in the image or the hook uses pip any more.

## Mutation evidence

The main agent was the primary producer, and the reviewer independently reran an equivalent batch. Each mutant was one exact-match substitution in a fresh copy of the library, run under the harness above, and every one failed its behavioral assertion:

| Mutant in `uv_install.sh` | Protected invariant | Failing case |
|---|---|---|
| `export --frozen` → `--locked` | the lock is exported without index revalidation, so it survives the proxy | "creates the venv, exports the frozen lock and syncs it" |
| `UV_INSECURE_HOST` not exported | proxy trust matches `pip_install.sh` | "set PYPI_PROXY becomes the uv default index with a derived insecure host" |
| `UV_DEFAULT_INDEX` not exported | installs go through the proxy | same |
| also `mkdir $HOME/.config/uv` | no persistent uv configuration that could leak the proxy into later `uv lock` runs | "writes no persistent uv configuration" |
| `UV_NO_CACHE` not exported | no cache left in the layer | all three environment cases |
| no `trap` cleanup | the temporary export is removed | "removes its temporary export file" |
| empty-export check bypassed | an export with no packages skips the sync | "skips the sync when the export selects no packages" |

For `update-dependencies.sh`, the main agent was again the primary producer and the reviewer reproduced the batch. The tests run a copy of the script under `tmp_path` with a stub `uv` first on `PATH`, so even the no-`cd` mutant stayed inside the test-owned directory. Every mutant was killed:

| Mutant in `update-dependencies.sh` | Protected invariant | Failing cases |
|---|---|---|
| `cd` removed | uv runs in the repository root wherever the script is invoked from | three: full upgrade, named packages, failed lock |
| `uv sync --locked` → `uv sync` | the venv is synced only against a lock that matches `pyproject.toml` | full upgrade, named packages |
| option check bypassed | option-like arguments never reach uv | both parametrized option cases |
| `uv lock … \|\| true` | a failed lock stops before the sync, with its exit status | failed lock |
| named packages also get `--upgrade` | naming packages upgrades only those | named packages |

The first helper batch was discarded as invalid evidence because the harness shared one HOME across calls, so a mutant's state leaked into later cases, and one substitution hit a comment instead of code. Both were corrected before the batch above was run. The reviewer also probed error propagation (a failing uv step exits with its status and leaves no temporary export) and checked that `uv venv --allow-existing` preserves an existing venv. No application Python changed, so the unchanged suite carries the application invariants.

## Limitations and cleanup

- **Deliberately not run:** a real `./update-dependencies.sh`, because it would apply the ten patch-level upgrades available on 2026-11-06 (for example ctranslate2 4.8.5 and youtube-transcript-api 1.2.5), and this change upgrades nothing ([D50](../DESIGN.md#d50) (5)). The user runs it as the first deliberate refresh.
- **Not performed here (no Docker):** an image build; a devcontainer rebuild with checks that `git status` stays clean, `uv sync --locked` succeeds, and `python` and `uvicorn` resolve to `/opt/venv`; a Compose smoke run of the API and every worker on GPU (CUDA loading from the venv) and CPU; a production-image check that dev tools are absent; and the library's Docker-based `tests/run.sh`. The user is to run these on the host.
- **Library publication:** done at the user's request. `main` was fast-forwarded to `252780a` and the annotated tag `v1.2.0` was pushed. `git ls-remote https://github.com/liboyin/docker-build-common.git 'refs/tags/v1.2.0^{}'` returned `252780a`, so the default Compose context resolves.
- **Accepted by design:** the image build does not check the lock against `pyproject.toml` (the devcontainer hook does), and the hook's dev install goes to PyPI directly, not through `PYPI_PROXY`.
- **Pre-existing and out of scope:** the library test "pip_install.sh rejects an empty lock file" expects exit 1, but library commit `1b8c221` made an empty lock exit 0, so that case fails when `tests/run.sh` runs.
- **Cleanup:** the scratch mirror process was stopped, a 32 KB `~/.cache/uv` created by this task's experiments was removed, and the reviewer removed its own scratch. Working evidence (patches, snapshots and reviewer probes) stayed in session scratch only; this record keeps its essential content.
