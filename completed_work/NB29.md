# NB29 — Task preparation remains coupled to the HTTP module

## Origin

TODO recorded a validated structural observation and proposed architecture improvement. `add_tasks` in the FastAPI module coordinated URL classification, filesystem resolution, response bookkeeping and Redis submission. NB25 had already made API imports resource-inert, and `resolve_filesystem_tasks` already separated glob expansion. The remaining proposal was to separate that preparation from HTTP. NB29 was executed as candidate 2 of the API group, after [N1](N1.md) and before NB15, and was committed and reviewed separately.

## Boundary

Move `POST /tasks` preparation into a small internal operation that returns the routed tasks and failed patterns. The endpoint keeps HTTP serialization and submits through the existing `queueing` functions. The user chose a new `youtube_whisperer/task_preparation.py` module for it, with `api.app.resolve_filesystem_tasks` forwarding the same object ([D42](../DESIGN.md#d42)). Compatibility surface:

- `POST /tasks` is unchanged: status 201, input/expansion order in the response, failed unmatched/directory-only patterns and local `none` sources, URL-before-filesystem submission, and best-effort partial submission with propagated errors under [D11](../DESIGN.md#d11).
- The `add_tasks` coroutine keeps its name and parameters.
- `api.app.resolve_filesystem_tasks` keeps the file-only, absolute-path NB16/NB22 behavior under [D13](../DESIGN.md#d13).
- The new module constructs no settings or Redis resources on import.

Non-goals: wire-schema changes, atomic submission, moving the worker's follow-up decision, and NB15's threading. Execution paused at the user's request between 12:53 and 13:50 UTC, partway through implementation, and the same implementation agent resumed it.

## Revalidation

At `16b0130`, `add_tasks` still held the classification loop, and `resolve_filesystem_tasks` lived in `api/app.py`.

## Change

[task_preparation.py](../youtube_whisperer/task_preparation.py) imports only `domain` and `models`. It defines:

- `PreparedTasks`, a frozen dataclass with ordered `successful`, `failed`, `youtube` and `transcription` tuples;
- `resolve_filesystem_tasks`, moved unchanged;
- `prepare_tasks(patterns)`, which classifies URL sources, fails local `none` sources without resolving them, resolves filesystem patterns and records failures.

In [app.py](../youtube_whisperer/api/app.py), `add_tasks` prepares the request, then submits each URL task and makes one transcription batch call when one is needed, then returns the response. The queue functions are still called through the `app` namespace. `resolve_filesystem_tasks = task_preparation.resolve_filesystem_tasks` keeps the existing import. This uses the same assignment form as `utils.is_url`, because Ruff rejects the redundant-alias re-export. DESIGN's component description, its import-inertness paragraph, its project structure and D42 now describe the module.

The four `resolve_filesystem_tasks` tests moved unchanged to [test_task_preparation.py](../tests/test_task_preparation.py). New tests there cover:

- a fresh-process import that loads no FastAPI, Starlette, Redis, settings or socket access;
- immutability of `PreparedTasks`;
- mixed submissions, with reverse-sorted glob results so that preserved order cannot pass as sorting;
- `none` sources never being resolved.

In [test_app.py](../tests/api/test_app.py):

- an identity test guards the forwarded import;
- the routing test uses owned files, an input order that differs from the submission order, and a single recorder for submission order;
- the `none` and failure-propagation tests use owned files instead of patching classification and resolution;
- the propagation test also asserts the D11 shape, where the URL is submitted before the transcription failure propagates.
