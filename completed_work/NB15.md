# NB15 — API handlers block the event loop with synchronous work

## Origin

TODO recorded a validated Non-blocking finding of medium severity. The API endpoints were `async def` but called synchronous Redis, glob, directory-traversal and deletion operations directly. In the single-process uvicorn service, a slow Redis call or a large traversal therefore stalled unrelated requests. The shared Redis pool deliberately has no read timeout. NB15 was candidate 3 of the API group, after [N1](N1.md) and [NB29](NB29.md), and was committed and reviewed separately.

## Boundary

No endpoint may run blocking Redis, glob, traversal or deletion work on the event-loop thread. Endpoints stay `async def` coroutine functions with unchanged names and parameters ([D18](../DESIGN.md#d18)), and each offloads its synchronous work with one threadpool call per request. The dependencies stay synchronous, because the installed FastAPI 0.141.1 already runs sync generator dependencies through `contextmanager_in_threadpool` and plain sync dependencies through `run_in_threadpool`; the main agent checked this against the installed source.

Compatibility surface: every HTTP contract is unchanged. Exceptions still reach the sanitized 500 handler, and the Redis client settings are unchanged. Non-goals: per-request timeouts, threadpool sizing, multiple uvicorn workers, and making [D6](../DESIGN.md#d6)/[D9](../DESIGN.md#d9) atomic.

The original boundary also required tolerating overlapping `DELETE /assets` requests. That vanished-file handling landed in N1, so NB15's acceptance kept only the concurrency tests and the requirement that N1's vanished-file tests keep passing.

## Revalidation

At `65d7483`, all seven endpoints still called blocking work directly on the event loop.

## Change

All seven endpoints in [app.py](../youtube_whisperer/api/app.py) now `return await run_in_threadpool(...)`.

- `get_tasks`, `clear_tasks` and `get_dead_letters` offload their existing `queueing` call.
- The other four endpoint bodies became synchronous functions with docstrings: `submit_tasks` (best-effort under D11), `delete_dead_letters` (read then delete, non-atomic under D9), `sorted_asset_paths`, and `remove_redundant_media` (N1's loop, including the vanished-file skip).

Correction (2026-10-11, [N13](N13.md)): this record originally called these functions endpoint internals "like the D42 helpers", but no user decision covered them, because D42 names only N1's helpers. N13 renamed them `_submit_tasks`, `_delete_dead_letters`, `_sorted_asset_paths` and `_remove_redundant_media`, so their internal status needs no D18 classification.

A new DESIGN subsection, "API requests do not block the event loop", records the design. It also records a limitation: anyio's default limiter has 40 tokens, shared with FastAPI's synchronous dependencies, and that caps how many requests can be blocked at once. Per-request timeouts and threadpool sizing remain unconfigured.

New tests in [test_app.py](../tests/api/test_app.py):

- A barrier test runs one `asyncio.run` with `httpx.AsyncClient` over `ASGITransport`. `GET /tasks` waits at a `threading.Event`; `GET /dead-letters` must complete while it is held; then the barrier is released and the held request is awaited.
- A test parametrized over all seven endpoints records which thread runs each dependency and each blocking call, and asserts that none ran on the event-loop thread.
- An `owned_worker_threads` fixture joins every thread a test started and fails if any is still alive.

Every wait is bounded by a 5-second safety timeout, and cleanup in `finally` releases and quiesces the held request.

## Limitations and cleanup

Responsiveness is bounded by the threadpool's capacity (40 tokens by default). Once that many requests are blocked, further requests queue for a token, and no per-request timeout applies. Overlapping `DELETE /assets` requests rely on N1's vanished-file skip. Overlapping clears remain non-atomic under D6/D9. No live uvicorn or Redis run was performed; the concurrency evidence comes from in-process ASGI tests. Scratch trees were deleted, and unrelated untracked files were preserved. A VS Code pytest-extension collection process seen during implementation was not owned by this run and was left alone.
