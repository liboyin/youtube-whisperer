# NB9 — Every started Azure recognition session is stopped

**Origin:** TODO recorded (Medium, validated by source inspection and a fake-recognizer reproduction with `started=1`, `stopped=0`) that `transcribe_audio_file` started continuous recognition and then inspected audio duration before entering its `try/finally` cleanup, so an `sf.info` failure left the session running. Startup failure was also outside the cleanup scope. NB9 was executed in an Azure failure-contract group after [N6](N6.md), which had corrected the function's failure documentation; the tasks were committed and reviewed separately.

**Boundary:** every session `transcribe_audio_file` starts is stopped on every exit path, failures write no output and propagate normally to the worker. `transcribe_audio_file` keeps preflight and existing-output consent, settings resolution, duration inspection, SDK configuration and SRT output; one private module-level function owns callback connection, start, wait, stop and result/error collection, without a session class. Start sits inside the cleanup scope, so stop is attempted after any start attempt, including one that raised, because a partially started native session cannot be distinguished. Preserved: synchronous completion; the `max(MIN_AZURE_TIMEOUT_SECONDS, duration * 1.5)` timeout and its `TimeoutError` message; empty-text filtering; callback registration order and debug logging; the start info log; the Azure cancellation `RuntimeError(error_details)` raised after stop; non-error cancellation completing normally; existing-output preflight skipping inspection and recognizer creation; prompt-consent reuse; and every module attribute tests patch. The compatibility surface — `transcribe_audio_file`'s signature, annotation, return values and exception types, plus `get_audio_duration_seconds`, `recognition_result_to_srt_block`, `MIN_AZURE_TIMEOUT_SECONDS` and `AzureWorker.dispatch_task` — is unchanged. Non-goals: behavior when `stop_continuous_recognition` itself raises (Python's default propagation remains), disconnecting callbacks, retry, timeout policy, and WAV conversion or worker changes.

**Revalidation:** at `d6d6851`, `azure_transcriber.py:112` started recognition and line 115 inspected duration before the `try/finally` at 116–120, confirming the leak.

**Change:** [azure_transcriber.py](../youtube_whisperer/transcriber/azure_transcriber.py) adds `_recognize_continuously(speech_recognizer, timeout_seconds)`, which connects the callbacks, logs the start, starts recognition inside `try`, waits, and always stops in `finally` before raising any Azure cancellation error and returning the non-empty results. `transcribe_audio_file` now computes the timeout after preflight and settings resolution and before building the SDK configuration or recognizer, so an inspection failure creates and starts nothing; it saves the SRT on the caller thread after the helper returns. The helper's recognizer parameter uses a quoted annotation because an existing import-isolation test stubs the SDK module without `SpeechRecognizer`. Observable ordering change: an unreadable file now fails before SDK configuration and before the start info log. [Tests](../tests/transcriber/test_azure_transcriber.py) add non-error cancellation saving partial results, duration failure creating no recognizer, startup failure stopping once without waiting or saving, and `KeyboardInterrupt` during the wait stopping once, joining owned callbacks and saving nothing; the existing timeout test also asserts that no SRT exists.

**Limitations and cleanup:** no live Azure session was exercised; behavior is verified against the SDK fakes, so whether `stop_continuous_recognition` is harmless after a failed native start is assumed rather than observed. Stop failures during an already failing path still replace the original exception (a recorded non-goal).
