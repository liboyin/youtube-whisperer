# NB18 — Supported YouTube URL forms resolve to video IDs

**Origin:** TODO recorded that `get_video_id` in [transcript_downloader.py](../youtube_whisperer/downloaders/transcript_downloader.py) rejected bare `youtube.com`, `m.youtube.com` and `/shorts/` URLs. Single-video expansion keeps the submitted URL, so the media download could succeed and caption routing then fail, dead-lettering the video, including download-only work.

NB18 was the first stage of a caption-path group with NB19 (caption HTTP timeouts) and NB24 (caption-service errors after download). It was committed on its own because it is functionally independent of them.

**Revalidation (`5fdb927`, 2026-10-10):** source inspection confirmed the parser compared `netloc` against only `youtu.be` and `www.youtube.com`, and accepted only `/watch` and `/live/`. It also found two malformed-input escapes:

- `/watch` without `v` raised `KeyError`.
- An empty `youtu.be` path returned `''`.

Installed yt-dlp's YouTube extractor (`extractor/youtube/_video.py`) uses `[0-9A-Za-z_-]{11}` for video IDs.

**Boundary:**

- **Intent:** accept the single-video URL forms the worker downloads, and reject everything else with `ValueError`.
- **Accepted forms:**
  - `http` or `https` URLs for `youtu.be/<id>`.
  - Host `youtube.com`, `www.youtube.com` or `m.youtube.com` with `/watch?v=<id>`, `/live/<id>` or `/shorts/<id>`.
  - Hosts are matched case-insensitively and without the port.
  - Extra query parameters and fragments are ignored, and one trailing slash after a path ID is tolerated.
  - IDs must match `[0-9A-Za-z_-]{11}`.
- **Malformed input:** includes unsupported hosts, schemes and paths, scheme-less text, missing, empty or invalid IDs, and extra path segments.
- **Non-goals:** `music.youtube.com`, `youtube-nocookie.com`, `/embed/` and `/v/` forms, scheme-less URLs, and canonicalising URLs during playlist expansion.
- **Assumption (non-material):** validating the ID shape rejects only strings that cannot be YouTube video IDs.

**Change:** `get_video_id` now:

- parses with `urlsplit`, so `;params` remain in the path and are rejected;
- reads `.port`, so a malformed or out-of-range port raises;
- requires an `http`/`https` scheme and matches `hostname`;
- reads `v` with a default;
- extracts `/live/` and `/shorts/` IDs, allowing one trailing slash;
- validates the ID with `re.fullmatch`.

Every rejection raises `ValueError(url)`. Callers and caption lookup are unchanged. The first candidate used `urlparse`; the switch to `urlsplit` and the port read came from the review finding below.

## Review

- **Reviewer:** an independent Codex session, `gpt-6.1-sol` at high effort, thread `01a12828-ccc5-7100-bffa-1c562bcc8f51`.
- **Assessment 1, on the `urlparse` candidate:** 1 Blocking finding.
  - **Finding:** `urlparse` moves `;params` out of the last path segment, so URLs such as `https://m.youtube.com/shorts/n9xhJrPXop4/;extra`, `youtu.be/<id>;x` and `/watch;x?v=<id>` were accepted. Reading `hostname` also skipped port validation, so `:abc`, `:65536` and `:-1` were accepted.
  - **Validated by the main agent**, which reproduced every example. It also confirmed that on Python 3.12.3 `urlsplit` keeps `;params` in `.path`, and that `.port` raises for those ports but returns 443 for `:443`.
  - **Disposition:** fixed, with regression tests and the two mutants above.
- **Follow-up assessment:** the finding was resolved and no new findings were raised. In reviewer scratch, 115 downloader tests and 26 probes passed with seed 1818. The probes covered rejection before caption-client creation, empty path parameters, and preservation of valid ports and URL decorations.
- **Verdict:** no blocking findings.
- **Integrity:** HEAD, status, in-scope hashes and modes, and out-of-scope untracked paths matched the frozen snapshot after both assessments.
- **Observation, not a finding:** URLs with userinfo (`user@youtube.com`) are still accepted. The boundary does not address them, and the host is still YouTube.
